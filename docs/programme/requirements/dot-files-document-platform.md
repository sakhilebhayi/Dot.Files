# MASTER IMPLEMENTATION PROMPT
# Dot.Files — Build the Premium Document Management, Storage, Preview and Collaboration Platform for the Entire Dot Ecosystem

## 1. THE VISION

Transform Dot.Files into a world-class business document management, storage, discovery, preview and collaboration platform.

Dot.Files must become the central document infrastructure for the entire Dot ecosystem, allowing businesses to securely store, organise, discover, preview, share, collaborate on and manage their documents across all authorised Dot platforms.

The experience must be effortless.

A business should be able to upload a document once, access it from different authorised platforms, collaborate with other users, maintain a complete document history and retain control over ownership, permissions and access.

Dot.Files must not simply be another cloud storage application. It should be an intelligent business document environment that understands the relationship between documents, businesses, users, teams and the platforms that use them.

The fundamental product principles are:

1. One authoritative document source.
2. One central identity through InfoDot.
3. Seamless access across authorised Dot platforms.
4. Actual visual document previews before opening files.
5. Flexible collaboration and sharing.
6. Complete, traceable version history.
7. Business-owner control and approval.
8. Strong security and tenant isolation.
9. A distinctive, premium product experience.
10. Consistent ecosystem familiarity where it matters.

**The vision: One document. One authoritative source. Many authorised ways to use it. A complete history of everything that happens to it.**

# PART B — FILE DISCOVERY AND VISUAL DOCUMENT PREVIEWS

## 7. Make Dot.Files a Visual Document Library

One of the most important features of Dot.Files must be the ability to identify documents before opening them.

Users should never have to rely exclusively on filenames, extensions or generic file icons to understand what they are about to open.

When browsing a business's document library, users should see actual visual representations of their stored documents.

**The preview must show what the actual file contains before the user opens it.**

This should become one of the defining features of Dot.Files.

## 8. Generate Actual Document Snapshots

Generate real document thumbnails and snapshots from the stored files.

Support appropriate previews for:

| File type | Preview expectation |
|---|---|
| PDF | Actual first page or representative page |
| Word | Actual document content and layout |
| Excel | Actual spreadsheet rows, columns and headings |
| PowerPoint | Actual slide thumbnail |
| Images | Actual image |
| Reports | Actual cover or representative page |
| Invoices | Actual invoice layout and relevant information |
| Contracts | Actual cover or representative page |
| Videos | Representative frame or thumbnail |
| Other formats | Appropriate preview where technically supported |

Never display fabricated content or generic illustrations as though they represent the actual document.

Where a format cannot be previewed, provide a polished fallback with useful metadata and a recognisable file-type representation.

## 9. Make File Recognition Immediate

When a user opens a folder or browses the document library, they should immediately recognise their files.

Each file representation should display useful information, where available:

- Actual document snapshot.
- File name.
- Document title.
- File type.
- Last modified date.
- Original creator or owner.
- Current version.
- Platform of origin.
- Sharing status.
- Relevant access indicators.

Provide beautiful grid and list layouts.

Users should be able to switch between visual browsing and information-rich document listings.

Support hover or selection interactions that reveal larger previews and contextual information without requiring users to open the complete document.

## 10. Intelligent Preview Generation

Implement a reliable document-preview generation pipeline.

Requirements:

- Generate previews when files are uploaded or imported.
- Generate new previews when relevant document versions are created.
- Ensure previews correspond to the correct version.
- Avoid unnecessary duplicate processing.
- Process large files asynchronously.
- Show processing states.
- Cache previews efficiently.
- Refresh previews when documents change.
- Handle corrupted, unsupported and password-protected documents gracefully.

Preview generation must not block normal document uploads or browsing.

## 11. Secure Preview Access

Previews must follow exactly the same access-control rules as the original document.

Implement:

- Private preview storage.
- Server-side authorisation.
- Tenant-aware preview access.
- Secure preview delivery.
- Appropriate cache invalidation.
- Access revocation.
- Protection against thumbnail exposure.
- Protection against sensitive document leakage.

A thumbnail must never become a security loophole that exposes information from a document the user cannot access.

## 12. Full Document Preview Experience

When a user selects a preview, provide a premium document-viewing experience.

Include:

- Large, high-quality preview.

# PART C — CENTRAL IDENTITY AND AUTHENTICATION

## 13. InfoDot Must Be the Only Authentication Gateway

Dot.Files must not have its own login, registration or independent authentication experience.

InfoDot is the central identity and authentication provider for the Dot ecosystem.

Users register and authenticate through InfoDot only.

Dot.Files consumes and validates the authenticated identity provided through the existing InfoDot SSO architecture.

## 14. Remove Local Authentication Pages

Dot.Files must not expose:

- Login pages.
- Registration pages.
- Sign-up pages.
- Independent password recovery pages.
- Duplicate authentication interfaces.
- Independent user-registration flows.

Audit all authentication-related routes, including:

- `/login`
- `/register`
- `/signup`
- `/forgot-password`
- `/reset-password`
- Email verification routes.
- Two-factor authentication routes.
- Custom authentication routes.
- Legacy authentication endpoints.

These are examples, not an exhaustive list.

## 15. Mandatory Server-Side Redirects

Every attempt to access a Dot.Files authentication page must redirect to the corresponding InfoDot authentication page.

Examples:

| Dot.Files request | Expected destination |
|---|---|
| Login | InfoDot login |
| Registration | InfoDot registration |
| Sign-up | InfoDot registration |
| Forgot password | InfoDot password recovery |
| Password reset | Appropriate InfoDot password recovery flow |
| Email verification | Appropriate InfoDot verification flow |
| Two-factor challenge | Appropriate InfoDot authentication flow |

Use the actual configured InfoDot authentication URLs.

Do not hardcode unverified production URLs.

Implement redirects at the Laravel routing and server-side middleware levels.

Do not rely on JavaScript redirects or hidden navigation links.

Preserve safe return destinations where appropriate, but never forward passwords, authentication tokens or session secrets through URLs.

## 16. Audit the Complete Authentication Architecture

Inspect:

- Web routes.
- Authentication routes.
- API routes.
- Route service providers.
- Authentication controllers.
- Middleware.
- Livewire components.
- Blade views.
- Authentication layouts.
- Installed authentication packages.
- Automatically registered routes.

Remove or retire independent local authentication routes without breaking legitimate SSO callback and session-management functionality.

Verify route caching and production configuration.

## 17. Seamless SSO Experience

Expected experience:

1. A user opens Dot.Files.
2. If already authenticated through InfoDot, Dot.Files opens normally.
3. If not authenticated, the user is redirected to InfoDot.
4. The user logs in through InfoDot.
5. InfoDot returns the user to the original authorised Dot.Files destination.
6. Dot.Files validates the identity, business context and permissions.
7. The requested document or workspace opens.

Handle expired and revoked sessions correctly.

Protect against open redirects, replay attacks and insecure token handling.

Never expose authentication secrets in URLs, logs or browser storage unnecessarily.

## 18. Central Identity and Business Context

Obtain the following through the authorised InfoDot identity infrastructure:

- User identity.
- User profile.
- Business membership.
- Tenant identifier.
- Roles.
- Permissions.
- Organisation context.

Dot.Files must not create duplicate identities or trust user-supplied tenant identifiers without server-side validation.

## 20. One Authoritative Document, Multiple Platform Experiences

Where possible, store one authoritative document in Dot.Files and allow authorised platforms to reference it.

Avoid unnecessary copies and uncontrolled duplication.

A platform should receive a secure document reference rather than unrestricted access to the underlying storage.

### Dot.Files to Dot.Docs

- User selects a document.
- User chooses Open in Dot.Docs.
- Dot.Docs receives an authorised document reference.
- Document opens in the appropriate editor.
- User edits the document.
- Changes are saved through the authorised integration.
- Dot.Files records the new version.

### Dot.Files to Spreadsheet Platform

- User selects a spreadsheet.
- Spreadsheet platform opens the authorised document.
- User views or edits according to permissions.
- Changes are saved through the controlled document integration.
- Version history is updated.

### Dot.Files to Dot.Finance

- Financial records and supporting documents are available to authorised financial workflows.
- Invoices and statements can be referenced without unnecessary copies.
- Document access and changes are recorded.

### Dot.Files to Dot.HR

- Authorised HR users can access employee documentation.
- Sensitive HR records retain their specific access policies.
- Access and changes are audited.

### Dot.Files to Dot.Projects

- Project teams can reference relevant documents.
- Project reports, specifications and contracts remain connected to their authoritative versions.

The architecture must support future integrations without requiring a separate document-sharing system for every platform.

## 21. Platform Document References

Create a reliable document-reference architecture.

Each reference should identify:

- Authoritative document.
- Business and tenant.
- Source platform.
- Destination platform.
- Authorised user or service.
- Permission scope.
- Reference status.
- Expiry, where applicable.

The destination platform must validate the reference through Dot.Files or the appropriate central authorisation service.

A reference must never become a permanent bypass around permission checks.

## 22. Controlled Document Synchronisation

When a platform genuinely requires a working copy, implement controlled synchronisation.

Requirements:

- Maintain a relationship between the original and derivative document.
- Track the source version.
- Track changes made in the destination platform.
- Detect conflicts.
- Avoid silent overwrites.
- Preserve historical versions.
- Record synchronisation status.
- Handle failed updates safely.
- Provide recovery mechanisms.

Clearly distinguish between an authoritative document, a working copy, an exported copy and a shared reference.

- Comment.
- Edit.

# PART F — VERSION HISTORY, DOCUMENT INTEGRITY AND FRAUD PREVENTION

## 26. Implement Comprehensive Version Control

Version history is a critical requirement.

Every meaningful document modification must be traceable.

Businesses must be able to investigate suspicious changes, resolve disputes and recover from accidental or malicious modifications.

For every version, capture:

- Version identifier.
- Document identifier.
- Business and tenant identifier.
- User responsible.
- Source platform.
- Date and time.
- Change type.
- Previous version reference.
- New version reference.
- File checksum or integrity information.
- Related activity and audit references.
- Approval status where relevant.

Where technically supported, capture meaningful document-level differences, including:

- Content changes.
- Added or removed pages.
- Spreadsheet modifications.
- Metadata changes.
- Structural changes.

Do not claim detailed content-level comparison for formats where reliable comparison is unavailable.

## 27. Premium Version History Experience

Create a clear, intuitive version history interface.

Authorised users should be able to:

- View previous versions.
- Identify who made each change.
- See when it happened.
- Identify which platform initiated it.
- Compare versions where supported.
- Preview historical versions.
- Download authorised historical versions.
- Restore previous versions.
- Review related activity.

Restoring an older version must create a new version.

Never erase the intervening history.

An ordinary editor must not be able to silently overwrite or manipulate the audit trail.

## 28. Tamper-Resistant Audit History

Protect audit and version records against unauthorised modification and deletion.

Use append-only or otherwise tamper-resistant mechanisms appropriate to the existing architecture.

Record important events, including:

- Upload.
- Download.
- Preview.
- Edit.
- Version creation.
- Version restoration.
- Share.
- Access approval.
- Access rejection.
- Permission change.
- Ownership transfer.
- Delete.
- Restore.
- Access revocation.
- Cross-platform synchronisation.
- Suspicious activity.

Users must not be able to remove evidence of their own actions.

## 29. Suspicious Activity and Fraud Prevention

Introduce document-governance monitoring to help businesses detect suspicious activity.

Consider:

- Unusual document modifications.
- Large-scale changes.
- Repeated modifications followed by deletion attempts.
- Unexpected ownership transfer attempts.
- Unusual sharing activity.
- Permission escalation.
- External sharing outside policy.
- Attempts to manipulate version history.
- Unexpected access patterns.
- Repeated restoration of previous versions.

Provide configurable alerts for business owners and authorised administrators.

Distinguish between:

1. Normal activity.
2. Unusual activity requiring review.
3. Policy violations.
4. Confirmed unauthorised activity.

Do not automatically accuse users of fraud based on behavioural indicators.

Any AI-assisted detection must provide explainable reasons and supporting evidence.

For high-risk actions, support configurable approval workflows and additional verification.

# PART G — SEAMLESS COLLABORATION WORKFLOW

## 30. End-to-End Sharing and Editing Experience

A typical workflow should operate as follows:

1. A user opens a document in Dot.Files.
2. The user chooses Share or Open in another platform.
3. The user selects the recipient or destination.
4. Dot.Files validates the user's permissions.
5. Required business-owner approval is obtained.
6. Dot.Files creates a secure, scoped document reference.
7. The destination platform or recipient receives authorised access.
8. The recipient opens the document.
9. The recipient views, comments on or edits according to permissions.
10. Changes are saved through the authorised integration.
11. Dot.Files records a new version.
12. The activity timeline is updated.
13. The business owner can review changes and revoke access if necessary.

The user should not have to download and re-upload documents unnecessarily.

The experience should be seamless across authorised Dot platforms, using the existing InfoDot SSO infrastructure.

## 31. Concurrent Editing and Conflict Resolution

If two users or platforms edit the same document simultaneously:

- Detect conflicting changes.
- Preserve both valid working states where possible.
- Avoid silent overwrites.
- Provide a clear conflict-resolution workflow.
- Record the final outcome in version history.
- Notify affected users where appropriate.

Do not claim real-time collaborative editing for formats or editors that do not support it.

Use the appropriate collaboration capabilities of each platform.

# PART M — REQUIRED REAL-WORLD TESTING SCENARIOS

## 46. Multi-User, Multi-Platform Testing

Do not limit testing to a single user or business.

Test with at least two independent business tenants and multiple users with different roles.

### Scenario 1: Basic Document Sharing

A business owner uploads a PDF to Dot.Files and shares it with an authorised colleague. The colleague can view it but cannot edit or delete it.

### Scenario 2: Cross-Platform Editing

A user opens a stored document in Dot.Docs, edits it and saves the changes. Dot.Files records the new version and updates the preview.

### Scenario 3: Spreadsheet Collaboration

A user opens a spreadsheet in the supported spreadsheet platform, makes changes and saves them. The changes are recorded without silently overwriting another user's work.

### Scenario 4: Ownership and Approvals

A user requests permission to share a confidential document with another platform. The business owner receives the request, reviews it and approves or rejects it.

### Scenario 5: Suspicious Modification

A user with editing permission makes unexpected changes to a document. The system records the changes, preserves the previous version and makes the activity visible to authorised administrators.

### Scenario 6: Version Restoration

A business owner discovers an incorrect modification and restores an earlier version. The system creates a new version and preserves the complete historical record.

### Scenario 7: Revoked Access

A business owner revokes a user's access. The user can no longer access the document through Dot.Files or an authorised platform reference.

### Scenario 8: Cross-Tenant Protection

A user from Business A attempts to access a document, preview, version or audit record belonging to Business B. Access must be denied.

### Scenario 9: Authentication Redirection

A user manually enters a Dot.Files login or registration URL. They are redirected to the correct InfoDot authentication page, and no local authentication interface is rendered.

### Scenario 10: Preview Before Opening

A user enters a business document library containing PDFs, spreadsheets, Word documents and presentations. Actual document snapshots are displayed so the user can identify documents without opening them.

### Scenario 11: Search Experience

A user searches for a document in Dot.Files. The search bar visually matches InfoDot, returns relevant authorised files and does not expose documents belonging to another business.

These scenarios must be tested through real application workflows, not simply mocked responses.
