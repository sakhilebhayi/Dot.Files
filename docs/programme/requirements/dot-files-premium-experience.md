Master Prompt: Transform Dot.Files into a Premium, Distinctive Product Experience

Vision

Let's elevate Dot.Files into a world-class file management and document experience with its own unmistakable identity.

Dot.Files is part of the wider Dot ecosystem, but it must not look, feel, or behave like InfoDot. It should have its own design language, personality, visual identity, user experience, tone of voice and product character.

Think of Dot.Files as a premium standalone software product that happens to be seamlessly connected to the Dot ecosystem.

The experience should make businesses feel that they are using a sophisticated, beautifully crafted digital workspace designed specifically for managing, discovering, previewing, organising and securely sharing their business information.

I want the design to feel intentional, elegant, modern, confident and exceptionally polished. Every screen, interaction, animation, piece of copy and visual detail should contribute to that experience.

Do not settle for a generic SaaS dashboard, a conventional cloud-storage interface or an InfoDot template with different colours.

Dot.Files must have its own taste.

1. Establish a Unique Dot.Files Design Identity

Before redesigning the interface, study the existing Dot ecosystem and the current Dot.Files implementation.

Understand the broader Dot brand, but deliberately establish a separate visual identity for Dot.Files.

Use all available design, UI/UX, product design, visual storytelling, branding, typography, layout, interaction design and creative direction skills.

Explore design inspiration from products known for exceptional design and document experiences, including:

* Apple — refinement, simplicity, visual hierarchy and attention to detail.
* Linear — precision, purposeful interactions and sophisticated interface design.
* Dropbox — file discovery, previews and effortless organisation.
* Notion — flexible workspaces and intuitive information architecture.
* Raycast — speed, keyboard-first interactions and compact, intelligent interfaces.
* Arc — distinctive product personality and thoughtful navigation.
* Google Drive and Microsoft OneDrive — familiar file management conventions, without copying their visual identity.

These are reference points, not templates to reproduce.

Create a distinctive Dot.Files visual language that includes:

* A recognisable visual identity and brand personality.
* A deliberate colour system.
* Premium typography and carefully controlled text hierarchy.
* Consistent spacing, alignment and proportions.
* Distinctive iconography and visual details.
* Thoughtful use of borders, surfaces, depth, shadows and contrast.
* Beautiful file and folder representations.
* A cohesive design system for every screen and component.

The result should be recognisably Dot.Files even when its logo is removed.

2. Give Dot.Files Its Own Personality

Dot.Files should communicate:

* Organisation.
* Clarity.
* Trust.
* Control.
* Intelligence.
* Professionalism.
* Simplicity.
* Security.
* Sophistication.

It should feel like a premium digital workspace for serious businesses.

Avoid:

* Copying InfoDot's layout or navigation.
* Reusing generic ecosystem dashboard templates.
* Excessive cards and unnecessary containers.
* Overloaded sidebars.
* Large decorative headings that consume useful space.
* Unnecessary gradients and visual effects.
* Generic AI-generated marketing language.
* Excessive animations that slow down the experience.
* Interfaces that look like an admin panel rather than a finished product.

Every design decision should have a purpose.

3. Use All Available Design and Copywriting Skills

Inspect the installed skills and available design resources before beginning.

Use every relevant skill that can improve:

* Product design and visual identity.
* UI/UX architecture.
* Typography and layout.
* Brand strategy.
* Interface copywriting.
* Product messaging.
* Content hierarchy.
* Microcopy and interaction feedback.
* Scroll-based storytelling and motion design.
* Accessibility and responsive design.
* Design systems and component consistency.

Do not merely read these skills and mention that they were used. Apply their guidance directly to the implementation.

Where multiple skills provide useful approaches, combine them into one coherent design direction rather than producing disconnected design ideas.

4. Redesign the Entire Dot.Files Experience

Review every existing screen and identify opportunities to improve the product experience.

The redesign should cover the entire application, including:

* Main workspace.
* File and folder browsing.
* Business document library.
* Recent files.
* Favourites and pinned documents.
* Search and filtering.
* File previews.
* Document details.
* File activity and history.
* File sharing.
* Permissions and approvals.
* Recycle bin and restoration.
* Storage and usage information.
* Settings and preferences.
* Empty, loading, error and success states.

Do not focus exclusively on the landing or dashboard screen.

The experience must remain visually consistent from the moment a user enters Dot.Files until they complete any file-management task.

5. Create an Exceptional File Discovery Experience

Files should be visually represented in a way that makes the workspace feel alive, organised and useful.

Support beautiful, meaningful file representations for:

* PDF documents.
* Word documents.
* Excel spreadsheets.
* PowerPoint presentations.
* Images.
* Videos.
* Reports.
* Contracts.
* Invoices.
* Business records.
* Other supported business file formats.

Where technically possible, generate actual document snapshots and thumbnails rather than displaying generic file icons for everything.

Users should be able to recognise important documents without having to open every file.

Include:

* High-quality document thumbnails.
* Useful file metadata.
* Clear file-type indicators.
* File names and descriptions.
* Last modified information.
* Owner or responsible person.
* Folder and platform origin.
* Relevant sharing and access indicators.

Provide intelligent viewing options, including grid, list and other layouts where appropriate.

The interface should make finding the right document feel effortless.

6. Make Document Previews a Signature Feature

The document preview experience should become one of the defining features of Dot.Files.

Users should be able to inspect documents quickly without downloading them or navigating away unnecessarily.

Design a beautiful preview experience with:

* Large, high-quality document previews.
* Appropriate rendering for supported formats.
* Page navigation for PDFs and other paginated documents.
* Image previews.
* Spreadsheet previews where supported.
* Document metadata.
* Version history.
* Activity history.
* Sharing and permission information.
* Contextual actions.

Previews must respect the same access permissions as the original documents.

Generate previews securely, store them privately and ensure that unauthorised users cannot access thumbnails, cached previews or generated files.

Where a format cannot be previewed, provide a polished fallback experience with the appropriate file information and available actions.

7. Make Dot.Files Feel Connected to the Entire Dot Ecosystem

Dot.Files should have its own identity, but it must function as the central file and document infrastructure for the wider Dot ecosystem.

Businesses should be able to access files associated with their authorised Dot platforms.

For example:

* Dot.Docs documents.
* Dot.Finance invoices and financial records.
* Dot.HR employee documentation.
* Dot.Mines operational reports.
* Dot.Analytics reports and exports.
* Dot.Projects project documentation.
* Other authorised Dot platform files.

Represent platform origins clearly without allowing platform branding to overwhelm the Dot.Files experience.

Users should be able to understand where a file originated, which platform uses it and where it can be accessed.

Do not assume every Dot platform is already integrated. Inspect the actual implementation and identify which integrations are operational, incomplete or missing.

8. Design Secure, Effortless Cross-Platform Sharing

Sharing should feel natural, fast and beautifully integrated.

Users should be able to share authorised files with other users, businesses and Dot ecosystem platforms without creating unnecessary copies or compromising security.

Design an intuitive sharing experience that includes:

* Selecting one or multiple files.
* Choosing an authorised recipient or destination platform.
* Selecting access permissions.
* Defining whether access is temporary or ongoing.
* Requesting business-owner approval where required.
* Viewing pending approvals.
* Viewing active shares.
* Revoking access.
* Viewing sharing history.

The business owner must retain the appropriate approval authority over business files and cross-platform access, subject to the organisation's configured governance policies.

A user must never gain additional access simply because a file has been shared with them.

All sharing operations must be validated server-side, tenant-aware, permission-controlled and recorded in an audit trail.

Maintain the distinction between sharing, moving and copying files.

9. Authentication Must Remain Centralised Through InfoDot

Dot.Files is part of the Dot ecosystem and must use InfoDot as its sole identity and authentication gateway.

Preserve the authentication requirements established previously:

* No independent Dot.Files login page.
* No independent Dot.Files registration page.
* No separate Dot.Files user-registration system.
* Unauthenticated users must be redirected to InfoDot.
* Authenticated InfoDot users should enter Dot.Files seamlessly.
* User identity, business membership, tenant context and permissions must be obtained from the authorised InfoDot identity infrastructure.

Dot.Files must maintain its own visual identity even though authentication is handled centrally through InfoDot.

The authentication experience should feel seamless without making Dot.Files look like InfoDot.

10. Make Motion and Interaction Feel Exceptional

Use scroll-motion and interaction-design skills to introduce subtle, purposeful movement.

Consider:

* Smooth transitions between file views.
* Elegant document-preview transitions.
* Responsive hover states.
* Subtle thumbnail interactions.
* Refined navigation transitions.
* Contextual menus.
* Drag-and-drop interactions.
* Smooth folder navigation.
* Thoughtful loading and progress states.
* Small interaction details that make the product feel responsive.

Motion should reinforce the experience, not distract from it.

Respect reduced-motion preferences, accessibility requirements and device performance.

Avoid unnecessary animations, excessive parallax and effects that compromise usability.

11. Write Exceptional Product Copy

Use all available content strategy, UX writing, brand voice and copywriting skills.

Dot.Files should have its own consistent tone of voice.

The language should be:

* Clear.
* Confident.
* Concise.
* Professional.
* Human.
* Helpful.
* Intelligent without sounding artificial.

Rewrite interface copy where necessary, including:

* Page headings.
* Navigation labels.
* Empty states.
* Search prompts.
* File descriptions.
* Sharing instructions.
* Approval messages.
* Permission explanations.
* Notifications.
* Error messages.
* Success messages.
* Onboarding content.
* Tooltips and contextual guidance.

Avoid generic phrases such as "Welcome to your dashboard" when a more useful, distinctive message can be written.

Copy should help users understand what they can do, what is happening and what action they should take next.

Do not use marketing copy to disguise missing functionality.

12. Technical and Implementation Requirements

Use Laravel Boost to inspect and understand the existing Laravel application before making changes.

Preserve the existing architecture and working functionality wherever possible.

Do not rebuild functioning systems unnecessarily.

Use the existing technology stack and conventions, including Laravel, Livewire and Tailwind where applicable.

The implementation must include:

* Reusable design-system components.
* Consistent responsive layouts.
* Accessible interactions.
* Efficient preview and thumbnail generation.
* Optimised asset loading.
* Secure file storage.
* Server-side permission enforcement.
* Tenant isolation.
* Reliable API and platform integrations.
* Appropriate background processing.
* Error handling and observability.
* Automated tests.

Do not introduce mock files, fake business activity, fabricated storage metrics or placeholder integrations to make the interface look populated.

Use real application data. Where no data exists, create a thoughtfully designed empty state.

13. Implementation Approach

Work in the following order:

Phase 1 — Product and design audit

* Inspect the existing Dot.Files application.
* Review all current screens and interactions.
* Inspect the wider Dot ecosystem's design language.
* Read all relevant installed design, copywriting, UX and motion skills.
* Identify what should be preserved, improved or replaced.
* Establish the new Dot.Files design direction.

Phase 2 — Design system

* Establish the Dot.Files visual identity.
* Define typography, colours, spacing, surfaces and components.
* Establish interaction and motion guidelines.
* Define the product voice and UX writing principles.

Phase 3 — Experience transformation

* Redesign the main workspace.
* Improve navigation and file discovery.
* Implement premium document snapshots and previews.
* Redesign sharing and approval experiences.
* Improve responsive behaviour and all application states.

Phase 4 — Ecosystem integration

* Preserve InfoDot authentication and identity integration.
* Verify business and tenant context.
* Verify cross-platform file access and sharing.
* Enforce owner approval and permission rules.
* Verify audit logging and revocation.

Phase 5 — Testing and refinement

* Test every redesigned screen.
* Test all major interactions.
* Test file previews across supported formats.
* Test permissions and tenant isolation.
* Test InfoDot authentication and session handling.
* Test responsive layouts and accessibility.
* Resolve visual inconsistencies and functional defects.

14. Definition of Done

The redesign is not complete simply because the interface looks different.

It is complete when:

* Dot.Files has a distinctive and recognisable visual identity.
* It no longer resembles an InfoDot interface or generic SaaS template.
* The entire application follows a coherent premium design system.
* File discovery and document previews are genuinely useful.
* Sharing is seamless, secure and governed by business permissions.
* InfoDot remains the sole authentication and registration gateway.
* Existing working functionality has not been broken.
* All major interactions work with real application data.
* The application is responsive, accessible and performant.
* Automated tests pass and critical security requirements are verified.

Provide a final implementation report identifying the design changes, skills applied, components built, functionality improved, integrations verified, tests executed and any remaining limitations.

Final Creative Direction

I want Dot.Files to feel like a product that businesses genuinely enjoy using.

It should be sophisticated enough to stand alongside the world's best file-management products, but distinctive enough that people recognise it as Dot.Files.

Do not make Dot.Files look like InfoDot with a different logo.

Give it its own identity, its own personality, its own visual language and its own experience.

InfoDot provides the identity and ecosystem connection. Dot.Files provides the premium file experience.

The final result should feel beautifully designed, effortless to use, intelligent in its functionality and exceptionally trustworthy.
